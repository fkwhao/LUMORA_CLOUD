# 结算恢复与对账

更新日期：2026-09-05。对应 LM-006、LM-005-R、LM-007-R、LM-015 和 DEC-001。

## 上线顺序与存储

1. 启动新版 Billing，由 Flyway 执行 `V9__preserve_expired_reservations_for_reconciliation.sql`。该迁移新增占用已返还标记及自动核对字段。只有旧系统以确切原因“预占超时，系统自动释放”关闭的记录会转为待对账，历史账本保留；明确人工或业务释放仍保持终态。
2. 为每个 Model Gateway 实例准备独占的持久目录，然后启动新版服务。升级和重启复用原目录；不能让两个运行中的实例同时访问同一目录，文件锁会拒绝第二个实例。
3. 发布新版前端。管理员入口为“结算对账”，用户在概览和订单查看待生效权益。

模型网关新增环境变量，示例也在 `backend/.env.example`：

| 变量 | 默认值 | 含义 |
| --- | --- | --- |
| `LUMORA_RECOVERY_JOURNAL_DIR` | `./data/billing-recovery` | 未完成结算命令目录；生产环境应配置固定绝对路径并保留底层存储。 |
| `LUMORA_RECOVERY_JOURNAL_MAX_ENTRIES` | `100000` | 未完成记录容量；达到上限会拒绝新请求，已有记录仍可恢复。 |
| `LUMORA_RECOVERY_MAX_ATTEMPTS` | `1000` | 每轮自动投递失败上限；达到后暂停，管理员可核对后恢复。 |

相对路径基于 Java 进程工作目录。当前 Compose 只启动中间件，Java 服务在本机运行，因此日志应配置在运行 Java 的主机。以后容器化时要单独挂载持久卷；实例替换前应保留旧实例目录，且先停止原实例再让替代实例接管该目录。

恢复日志包含请求 ID、操作、已取得的用量/费用/计价版本、时间及重试状态，不保存请求正文或密钥。未完成记录不按时间过期；只能在 Billing 确认操作完成后清理。不得以清空目录的方式处理卡住的请求。目录容量用尽、不可写或存在损坏记录时，应先恢复存储或核对记录。

每条日志先强制写入文件，再原子替换。Linux 上还同步目录；Windows Java 文件接口没有目录 fsync，此处只保证文件内容强制写入和原子替换。文件日志没有跨磁盘复制，无法找回未成功落盘或已经丢失的磁盘内容。

## 恢复规则

调用供应商前检查恢复日志的可写性和容量，失败会返回 `BILLING_RECOVERY_UNAVAILABLE`。取得最终处理依据后，先写日志，再调用 Billing；Redis 调度失败不妨碍该日志保留。失败投递按 10 秒到 300 秒退避，扫描默认每 10 秒一次，达到次数上限后暂停并展示原因。

如果 Billing 已成功但响应丢失，后续重放保持原请求 ID、用量 ID 和费用依据，Billing 的行锁、唯一约束和终态规则防止重复扣减。辅助 Redis 中的旧记录不会覆盖已存在的日志或重新激活暂停记录。仅存在于 Redis 的旧命令会在投递前导入文件日志；升级前已经丢失的记录无法凭空恢复。

到期预占只返还尚未返还的占用额度，并保留 `PENDING_RECONCILIATION`。迟到的可靠用量仍归原额度桶；原桶不足时保留待处理，不转扣新周期、不挤占其他请求。手工明确释放仍是终态。

Billing 自动核对只使用已经落入用量表的权威记录，足额时结算并记录审计；缺用量或额度不足时写明原因，延后 5 分钟再次核对。扫描不会自动获取供应商账单，也不会以预占金额代替真实用量。网关暂停记录要先恢复投递，才可能将其用量补入 Billing。

可选 Billing 配置：

| Spring 属性 | 默认值 | 作用 |
| --- | --- | --- |
| `lumora.billing.reconciliation.enabled` | `true` | 启用自动核对。 |
| `lumora.billing.reconciliation.batch-size` | `100` | 每轮扫描上限，限制在 1–1000。 |
| `lumora.billing.reconciliation.scan-interval` | `PT1M` | 扫描间隔。 |
| `lumora.billing.reconciliation.initial-delay` | `PT1M` | 启动后首次扫描延迟。 |

扫描中的单条异常独立记录，不回滚其他记录。缺证据记录可以持续待处理，但到期后不再占用预占额度。

## 管理员操作

管理页路径为 `/admin/reconciliation`。查询、单条处理、批量操作和恢复投递都校验可信网关身份及 ADMIN 权限。

| 方法与路径 | 行为 |
| --- | --- |
| `GET /api/admin/billing/reconciliation` | 按状态、请求 ID、用户和页码查询；默认待对账，状态 `ALL` 包括已结算与已释放。 |
| `GET /api/admin/billing/reconciliation/{requestId}` | 预占、用量、核对状态与账本审计详情。 |
| `POST /api/admin/billing/reconciliation/{requestId}` | 单条结算或释放，原因必填；缺少用量时允许依可核实材料补录。 |
| `POST /api/admin/billing/reconciliation/batch` | 最多 50 条，原因必填，逐条事务和结果；批量结算必须已有用量。 |
| `GET /api/admin/model-gateway/recovery` | 当前网关实例恢复队列，每页 20 条。 |
| `POST /api/admin/model-gateway/recovery/{requestId}/retry` | 原命令恢复投递，原因必填，记录管理员及依据，成功返回 204。 |

费用和用量已有权威记录时不能通过人工核对改写；人工释放表示核对后明确关闭，必要的汇总纠正在同一事务完成。批量部分失败会分别返回原因，重试成功项不会产生第二次账务变化。人工与自动竞争时只允许一个终态。

恢复队列是实例本地视图；多个实例需分别访问其队列，当前不提供跨实例聚合。恢复投递仅重置重试状态并保存本次操作说明，不修改原用量；最终账务处理审计保存在 Billing 账本。日志完成后会清理，恢复按钮的操作说明不替代长期账务审计。

## 续费展示与预占估算

用户概览展示当前权益及按时间排序的待生效套餐；订单显示权益起止时间和状态。购买不同套餐也按已有订阅和排期顺延。接口只返回该用户拥有的订阅。

普通文本预占使用完整请求 JSON 的 UTF-8 字节数、25% 余量、256 固定开销及每条消息 16 的开销，最多取模型上下文窗口；最大输出、最高相关输入单价、最低额度及原时间倍率继续适用。该估算不是实际 tokenizer，也不改变最终按供应商 Usage 结算。

图片、音视频、文件、服务端历史引用、托管搜索等输入不受当前请求体量可靠约束时，回退到全窗口估算。真实用量超过预占时按待对账规则处理，不能因此占用其他请求额度。额度不足提示包含预占需求和可用额度。
